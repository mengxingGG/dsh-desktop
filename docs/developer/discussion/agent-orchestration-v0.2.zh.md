## 1. 目标与边界

要解决的问题：多家订阅分散，各家模型各有所长，人不会每次选对，上下文还要来回复制。

产品形态：一个项目房间里的班组。用户只和厂长说话，厂长按岗位把活分给已订阅的官方开发工具（Claude Code、Codex 等）。不是「一个窗口里点很多模型」。

第一版只做软件开发班组。美术 / 建模以后按同样「工种 + 工作目录 + 会话绑定」扩编。

明确不做（第一版）：多用户、代持别人的 Key、系统自动选厂长、用户直接和子智能体对话、每条命令弹权限、复用 DeepSeek 消耗查询去查其他家。

合规立场：所有模型调用都发生在各家官方 CLI 进程内，DSH 只负责启动、传参、收结果。不提取任何一家的登录凭证直连 API。

## 2. 已决事项

以下是本方案的前提，后面各节据此展开。

| 事项 | 决定 | 一句话理由 |
|---|---|---|
| 厂长怎么派活 | crew 插件内置一个 MCP server，厂长引擎以 MCP 工具调用 `dispatch / append / stop / status / integrate / commit` | 厂长是跑在 CLI 里的模型，不能自己 spawn 进程 |
| 厂长运行形态 | 常驻进程，同一会话；每回合以结束语收尾后空闲；有事件时由 crew 主动注入消息唤醒 | 工人耗时不确定，厂长不能占着模型等 |
| 工人运行形态 | 一次派工 / 追加 = 一次有界的无头运行（`-p` 类），按 session_id 恢复 | 工人的工作天然有界，不需要常驻 |
| 工人隔离 | 派工时建好模块目录，工人 cwd 在模块目录内，目录内 `README.md` 为工单；靠提示词 + 各 CLI 自身围栏 + 第二层审批 | 单人自用，模型一般不会跑出来；不引入 worktree |
| 状态灯来源 | 引擎结构化输出 / 退出码 + 停工协议标记 + crew 收工硬检查 | 「完成」不能信工人自述 |
| git 提交 | 只有厂长，且必须经 `crew.commit` 门禁；厂长引擎本身不给 git 写权限 | 规则强制，不靠提示词 |
| 登录 | 拉起各 CLI 自己的交互登录（需 PTY）；DSH 只探测登录态 | 不做无头登录 |
| 会话过长 | 允许作为第四种新开会话的条件，新开前写交接摘要 | 长会话每轮带全部历史，配额随长度增长 |

## 3. 系统架构

```text
┌──────────────────────── DSH 桌面壳 / Web ────────────────────────┐
│  中间：厂长对话        右侧：工人列表        设置：岗位表 + 登录额度  │
└──────────────┬──────────────────┬─────────────────────┬───────────┘
               │                  │                     │
        ┌──────▼──────┐    ┌──────▼──────┐       ┌──────▼──────┐
        │    crew     │    │    roles    │       │  providers  │
        │ 编排 + MCP  │◄───│  岗位表     │◄──────│ 五家适配器  │
        └──────┬──────┘    └─────────────┘       └──────┬──────┘
               │  MCP 工具                               │ 启动 / 登录 / 额度
        ┌──────▼──────┐                          ┌──────▼──────┐
        │ 厂长进程     │  crew 注入事件消息        │ 工人进程 ×N  │
        │ (常驻)      │◄─────────────────────────│ (有界运行)   │
        └─────────────┘                          └─────────────┘
```

三个插件，不揉进现有 DeepSeek 消耗查询插件：

| 插件 | 职责 |
|---|---|
| providers | 五家各自适配：探测 CLI、能力矩阵、启动参数拼装、拉起登录、登录态与额度查询、输出流归一化。DeepSeek 继续走现有消耗插件，在设置里占「DeepSeek（API）」一行。 |
| roles | 岗位表读写（角色 → 引擎 + 模型 + 思考档）；改表只影响下一单；进行中工单锁开工时的绑定；保存时校验引擎能力与登录态。 |
| crew | 派工板（board）、会话绑定、厂长运行时（常驻 + 唤醒）、工人运行时、停工协议解析、收工硬检查、审查 / 整合流程、提交门禁、右侧列表数据、MCP server。 |

编排状态以 crew 的 board（含 session_id 映射）和仓库内 `docs/` 为准，不只活在插件内存里（DSH 仍会破兼容）。

工作室代码与业务仓库分开。工人默认不得改工作室自身插件代码，除非当前打开的就是这个仓库。

## 4. 运行模型

### 4.1 厂长：常驻 + 唤醒

- 每个项目一个厂长进程、一只会话。进程由 crew 启动并保持 stdin 打开，以流式 JSON 收发消息（Claude Code 可用 Agent SDK 的长会话模式或 `-p` 的流式输入模式，具体参数以当前 CLI reference 为准；其他引擎按其能力选等价方式或 PTY）。
- 若某引擎没有长驻无头模式，适配器退化为「每次唤醒 = 一次 `-p --resume`」。对外接口一致：`ManagerRuntime.send(message)`。
- 厂长每回合以结束语收尾，回合结束（收到 result 事件）后进程留存但不消耗模型。厂长不轮询、不 sleep、不「等」。
- 唤醒 = crew 向厂长会话注入一条消息。用户消息和 crew 事件消息进同一个 FIFO 队列，厂长回合中不注入，回合结束后取下一条。
- DSH 重启或进程死亡：按 session_id resume；resume 失败走第 5 节的会话恢复。

结束语约定（进入厂长提示词）：每回合最后一行固定为 `等待：<模块列表 | 用户 | 无>`，供右侧展示「厂长在等什么」。

### 4.2 工人：一次派工 = 一次有界运行

- `dispatch` / `append` 各启动一次无头进程，cwd = 模块目录，传入工单与权限参数，按 session_id 恢复。
- 进程退出即回合结束。状态由退出码 + 收工报告 + 硬检查共同判定（第 8 节）。
- `stop`：先发 SIGINT 结束当前回合（Claude Code 已确认：SIGINT 结束回合，SIGTERM 会留下未完成回合，resume 时继续），超时再 SIGTERM。

### 4.3 工人状态机

```text
queued ──启动──► running(绿)
running ──收工报告 done + 硬检查通过──► done(无色) ──厂长 append──► running
running ──收工报告 blocked / 权限被拒 / 硬检查未通过超次──► paused(黄) ──处理后 append──► running
running ──退出码非零 / 进程死亡 / 会话恢复失败 / 连续失败──► failed(红) ──换人或修复──► running
```

- 黄 / 红都带 `reason`（枚举 + 原文），进右侧详情。
- `done` 不销毁会话，只是空闲；被追加则回到 running，仍是同一行。

### 4.4 事件与唤醒（补充）

每次唤醒都是厂长引擎的一个回合，消耗厂长额度。因此：

- 唤醒事件只有：开发完成（硬检查通过并已自动转审查）、审查通过、审查打回超次、整合结论、黄灯、红灯。
- 进度事件（工人还在跑、审查进行中）不唤醒，只更新右侧。
- 事件合并：同一时间窗（默认 5 秒）内的多个事件合并为一条消息。

事件消息格式：

```text
[crew事件 2026-09-04 14:03]
- 模块 auth：开发完成，收工检查通过，已自动转审查
- 模块 payment：黄灯（需要依赖）：stripe@^14 —— 工人原文：……
- 模块 report：审查通过（第 2 轮）
```

## 5. 会话绑定

后台绑定键：`项目 + 角色 + 模块 → session_id`，由 crew 维护，用户不复制粘贴。

| 角色 | 会话粒度 | 说明 |
|---|---|---|
| 厂长 | 每项目一只 | 常驻，重启 resume |
| 开发 | 每模块一只 | 打回修复、用户追加，都同一 session_id |
| 审查 | 每工单一只 | 能 resume 则 resume |
| 整合 | 每工单一只 | 同上 |

允许新开会话的条件（只有这四种）：

1. 新模块。
2. 用户换了该角色的引擎（换引擎 = 换人）。
3. 旧会话确认恢复不了。
4. 会话过长：超过 roles 中配置的阈值（回合数，或适配器观察到引擎发生了上下文压缩）。新开前，crew 先向旧会话追加一次「写交接摘要到 `docs/log/<模块>-dev.md`」，成功后再开新会话，新会话的第一条消息指向该摘要。厂长会话同理，交接写入 `docs/project.md` 的「当前状态」节。

磁盘是兜底：会话死了，从 `docs/`、`tests/` 恢复后再开工，不能从空白开始。

Claude Code 已确认：session_id 在 `--output-format json` 的结果里；`--resume <id>` 可从任意目录恢复（v2.1.223 起，此前只能在同一项目目录）。其他引擎的 resume 机制待逐家确认（第 12 节）。

## 6. 目录、工单与磁盘契约

### 6.1 仓库布局

```text
<业务仓库>/
  src/<模块>/                 # 模块目录 = 工人 cwd（目录名由模块规格指定，默认 src/<模块>/）
    README.md                 # 工单，crew 从模块规格 + 角色模板渲染，工人只读
    ...                       # 模块代码
  src/shared/                 # 厂长铺场时写好的公共接口 / 类型 / 桩，工人只读
  docs/
    project.md                # 厂长维护的总规格：目标、模块划分、接口契约、依赖顺序、当前状态
    modules/<模块>.md          # 模块规格：目标、非目标、接口、验收、模块目录、测试路径与命令
    log/<模块>-dev.md          # 开发记录，完成后不得删；含交接摘要
    log/<模块>-review.md       # 审查记录
    log/integrate.md          # 整合记录
  tests/
    <模块>.*                   # 测试脚本，完成后不得删，与模块规格对应
```

crew 自身的运行数据（board、原始输出流、工人日志）放在 DSH 数据目录 `<dsh_data>/crew/<仓库标识>/`，不进业务仓库，不需要改 `.gitignore`。

### 6.2 工单（README.md）由谁写

厂长写 `docs/modules/<模块>.md`（规格），调用 `crew.dispatch` 时 crew 建目录并把规格 + 角色模板渲染成 `README.md`。这样规格只有一份，工单是它的派生物；厂长不手写第二份。若你希望厂长直接手写 README，把渲染步骤关掉即可，接口不变。

### 6.3 契约

- 开发收工必须同时有：模块规格、开发记录、对应测试，且测试命令能跑、能过。
- 审查对照规格；检查 `git diff` 路径是否越权；测试是否覆盖验收且能跑。
- 整合只收「审查通过」的模块，跑全量 `tests/`，写整合记录，再交厂长。
- 以后美术等工种按同样规则加目录（如 `assets/`），主流程不改。

## 7. 围栏与权限

### 7.1 铺场与分工

| 事项 | 谁做 |
|---|---|
| 脚手架、锁文件、依赖安装、测试命令能跑、`src/shared/` 接口与桩 | 厂长，派工前完成 |
| 工人中途要新依赖 | 工人停（黄），厂长决定并安装，再 append 开工；工人不改环境 |
| 模块内写代码、跑该模块测试 | 工人，围栏内全自动 |
| 写出围栏（出目录、改全局配置、乱联网） | 停（黄），厂长通知用户 |
| `git add` / `commit` | 仅厂长，经 `crew.commit` |
| 交付前读 docs 与抽查代码、向用户确认 | 厂长 |

厂长装依赖前先 `crew.status()`；若有工人 running，等其转 done / 黄 或先 `stop`，避免锁文件和 `node_modules` 在工人跑测试时变动（见风险登记 R1）。

### 7.2 工人可写范围

开工时按模块收紧，只允许写：

- 模块目录（`src/<模块>/`，或规格写明的路径白名单）
- `docs/modules/<模块>.md`、`docs/log/<模块>-*.md`
- `tests/<模块>.*`

其余仓库内容只读。禁止：git 写操作（`add / commit / checkout / reset / stash / push`）、包管理器安装、改全局配置、出仓库。允许：`git status / diff / log`、规格里写明的测试命令。

补充（实现细节）：工人 cwd 在模块目录，而 `docs/`、`tests/` 在仓库根，属于 cwd 之外。对 Claude Code 需要 `--add-dir <仓库根>` 把仓库挂进来，再用 settings 的 `permissions.deny` 限制 `Edit / Write` 路径，用 `--allowedTools` 白名单 Bash 命令（权限规则语法如 `Bash(git diff *)`，尾部空格加星号为前缀匹配）。其他引擎的「可写根目录」机制待确认。

### 7.3 第二层审批（黄灯的机制）

- 围栏内不弹窗。
- 工人触碰围栏时，引擎会拒绝或请求权限。Claude Code 已确认两条路：
  - 无权限宿主：直接拒绝，stream-json 里出现 `permission_denied` 系统消息，最终结果列出 `permission_denials`；可加 `--permission-prompts none` 让模型不重试。
  - 有权限宿主：`--permission-prompt-tool <MCP 工具>` 或 Agent SDK 的 `canUseTool` 回调，把请求交给 crew 回答。crew 收到即转黄，用户在右侧工人详情里批准 / 拒绝 / 设「此类全自动」。
- 其他引擎若无头模式被拒即退出，则「批准」的语义 = 用放宽后的围栏 `append` 恢复。UI 文案统一为「批准并继续」。

## 8. 停工协议与收工检查

### 8.1 收工报告（工人回合末尾必须输出）

```json
{
  "status": "done | blocked | failed",
  "reason": "dependency | permission | test_red | unclear_spec | other",
  "summary": "一段话",
  "needs": ["stripe@^14"],
  "files_changed": ["src/payment/..."],
  "tests": { "command": "...", "passed": true }
}
```

- Claude Code 用 `--output-format json --json-schema` 直接拿结构化输出（已确认，字段在 `structured_output`）。
- 其他引擎：适配器解析最终消息中的 ```json 围栏块；解析失败按 failed 处理。
- 工人不向用户提问；`unclear_spec` 也是 blocked，交厂长。

### 8.2 状态判定（crew 执行，不信工人自述）

1. 退出码非零 → 红（附 stderr 与最后的错误分类）。
2. 报告 `blocked` → 黄，reason 透传。
3. 报告 `done` → 硬检查：
   - `docs/modules/<模块>.md`、`docs/log/<模块>-dev.md` 存在且本次有更新；
   - 规格中写明的测试路径存在；
   - crew 自己跑规格中的测试命令，必须通过；
   - `git status --porcelain` 中的改动路径全部在白名单内。

   全部通过 → done 并自动转审查；任一不过 → 自动 `append` 一次「收工检查未通过：…请补齐」；再不过 → 黄，reason = `handoff_check_failed`。
4. 每张工单的硬上限（roles 可配）：最大回合数（Claude Code 用 `--max-turns`）、最长墙钟时间、每项目并发工人数。到顶 → 黄，reason = `budget`。

### 8.3 停工原因（展示用，不是封闭列表）

等围栏外权限、要新依赖、额度尽、登录失效、网络失败、审查打回超次、测试红、进程死亡、收工检查未通过、超预算。

Claude Code 已确认：API 重试事件 `system/api_retry` 带 `error` 分类（`authentication_failed`、`rate_limit`、`billing_error`、`overloaded`、`server_error` 等），`error_status` 为 null 表示无 HTTP 响应的连接错误。适配器据此区分「登录失效」「额度尽」「网络失败」，比看退出码准。其他引擎各自找对应信号。

## 9. 审查与整合流程

```text
开发 done + 硬检查通过
  └─► crew 自动派审查（绑定本工单会话）
        ├─ pass  ──► 事件唤醒厂长
        └─ reject ─► crew 直接 append 到开发会话（附问题清单），不经厂长
                     打回次数 ≥ N（默认 3）──► 黄，唤醒厂长
全部模块 pass
  └─► 厂长调用 crew.integrate()
        └─► 整合工人：跑全量 tests/，写 docs/log/integrate.md，输出结论
              ├─ pass  ──► 唤醒厂长 → 厂长抽查 → 向用户交付 → crew.commit
              └─ fail  ──► 唤醒厂长，附失败模块与日志；厂长决定 append 哪个模块
```

审查结论格式：

```json
{ "verdict": "pass | reject", "issues": [{ "file": "...", "line": 0, "problem": "...", "expected": "..." }] }
```

## 10. crew MCP 工具接口

只暴露给厂长引擎。返回值一律短（状态级），不回灌工人日志——日志走磁盘与右侧面板，避免厂长会话被撑爆。

| 工具 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `crew.dispatch` | `module`, `role`(dev) | `{job_id, session_id, status}` | 读 `docs/modules/<module>.md`，建目录，渲染 README，按岗位表启动工人。规格缺字段则报错不启动。 |
| `crew.append` | `module`, `message` | `{job_id, status}` | 追加到该模块绑定会话；done → running。 |
| `crew.stop` | `module` | `{status}` | SIGINT → 超时 SIGTERM。 |
| `crew.status` | `module?` | board 摘要 | 每行：模块、角色、引擎、状态、reason、最近一句。 |
| `crew.reassign` | `module`, `engine`, `model?` | `{job_id, session_id}` | 换人：新会话，第一条消息指向 `docs/log/<module>-dev.md` 恢复。 |
| `crew.integrate` | — | `{job_id}` | 只在全部模块审查通过时可调，否则报错列出未通过模块。 |
| `crew.commit` | `message` | `{commit_hash}` 或拒绝原因 | 门禁：有工人 running 则拒绝；提交时排除 DSH 运行数据。 |

厂长引擎自身的权限：仓库根可写（铺场需要），Bash 允许包管理器与测试命令，禁止 git 写操作（提交只能走 `crew.commit`）。

## 11. 提示词规范

各家引擎的注入方式不同：Claude Code 用 `--append-system-prompt-file`（已确认；不用 `--bare`，因为 bare 模式不读订阅登录，且不加 `--bare` 时 `-p` 会加载业务仓库的 `CLAUDE.md`、`.claude/settings.json`、`.mcp.json`，角色指令不要去改业务仓库自己的这些文件）。其他引擎按其机制（AGENTS.md / GEMINI.md / 系统提示参数）注入，待确认。

### 11.1 厂长提示词（骨架）

厂长及其重要，以下是必须写进去的内容；措辞可改，条目不减。

**身份与边界**
- 你是本项目的厂长。只有你和用户对话；用户看得到工人，但不会和工人说话。
- 你不写模块代码。模块开发一律派工。你做：需求澄清、总规格、铺场、派工、处理事件、验收、交付、提交。
- 你不替用户决定换模型、换引擎。额度尽或工人红灯时，说明原因，给出「自己处理」或「换某个已订阅工具接着干」两个选项，等用户选。

**流程**
1. 需求澄清：和用户确认目标、非目标、验收。
2. 写 `docs/project.md`：模块划分、接口契约、依赖顺序、测试策略。
3. 铺场：脚手架、依赖、锁文件、测试命令跑通、`src/shared/` 里的接口 / 类型 / 桩。派工前完成。
4. 为每个模块写 `docs/modules/<模块>.md`，再 `crew.dispatch`。
5. 每回合处理 `[crew事件]`，按事件表行动，以结束语收尾。
6. 全部审查通过 → `crew.integrate`。
7. 整合通过 → 读 `docs/`、整合记录、测试结果，抽查 diff（不读全库）→ 向用户交付 → 用户认可后 `crew.commit`。

**模块拆分原则**
- 接口先行：先在 `docs/project.md` 和 `src/shared/` 定好模块间接口，再拆；工人只依赖接口，不依赖别的模块的实现。
- 每个模块独立可测：对它依赖的其他模块，铺场时提供桩 / 假实现，或按依赖拓扑序派工（基础模块 done 且审查通过后再派依赖它的模块）。不允许「等另一个模块做完才能跑测试」的模块同时开工。
- 一个模块 = 一个开发会话能做完的量。做不完就再拆。
- 两个模块不改同一个文件；共享代码归 `src/shared/`，由你在铺场时写。
- 模块规格必须含：目标、非目标、接口（输入输出、错误）、验收条目、模块目录、测试路径、可在模块目录内独立运行的测试命令。

**事件处理表**

| 事件 | 动作 |
|---|---|
| 开发完成（已转审查） | 无需动作，结束语记录 |
| 审查通过 | 若全部通过 → `crew.integrate`；否则记录 |
| 审查打回超次 | 读 `docs/log/<模块>-review.md`，判断是规格问题还是实现问题；规格问题改规格后 append，实现问题带明确指示 append |
| 黄：需要依赖 | 先 `crew.status`；安装（无工人 running 时）；`crew.append` 告知已装 |
| 黄：围栏外权限 | 告知用户，等用户在右侧批准或指示 |
| 黄：规格不清 | 向用户确认，改规格，append |
| 黄：超预算 | 判断是否再给一轮；或拆模块 |
| 红：额度尽 / 登录失效 / 网络 | 告知用户原因与两个选项，等用户 |
| 红：进程死亡 / 会话丢失 | `crew.reassign` 同引擎重开（从磁盘恢复）；再失败告知用户 |
| 整合失败 | 定位失败模块，append 修复；不要自己改代码 |

**用户改需求**
- 加需求 / 改需求 / 返工，全部 `crew.append` 到原模块会话，不新开。改岗位表只影响下一单。

**回合规范**
- 不轮询、不 sleep、不「等待中……」；派完工直接结束回合。
- 最后一行固定：`等待：<模块列表 | 用户 | 无>`。
- 与用户同语言。

**禁止**
- 直接改模块代码；在工人 running 时 commit（工具会拒绝）；把工人日志大段复述给用户（用摘要，让用户看右侧）。

### 11.2 开发工人工单（README.md 模板）

```markdown
# 工单：<模块>

## 目标 / 非目标
<来自 docs/modules/<模块>.md>

## 接口
<来自规格；共享类型见 ../shared/>

## 验收
<条目>

## 你的工作范围
- 可写：本目录；../../docs/modules/<模块>.md；../../docs/log/<模块>-*.md；../../tests/<模块>.*
- 只读：仓库其余部分
- 测试命令：<在本目录可独立运行>

## 必须做
- 开发记录写入 ../../docs/log/<模块>-dev.md（过程、决定、未尽事项），完成后不得删
- 测试写入 ../../tests/<模块>.*，与验收条目一一对应，完成后不得删
- 收工前跑测试命令，必须通过

## 禁止
- 安装依赖、改环境、改全局配置、改本目录之外的代码
- 任何 git 写操作
- 向用户提问：遇到自己解决不了的，停下来，按下面格式报告

## 收工报告（回合末尾必须输出）
<第 8.1 节的 JSON schema>
```

### 11.3 审查工人

输入：模块规格、`git diff`、开发记录、测试路径。做：对照规格逐条核验收；检查改动路径是否越权；跑测试。输出第 9 节的结论 JSON，写 `docs/log/<模块>-review.md`。不改代码。

### 11.4 整合工人

输入：全部审查通过的模块清单、`docs/project.md`。做：跑全量 `tests/`；检查模块间接口对接；写 `docs/log/integrate.md`。输出 `{verdict, failing_modules, notes}`。不改代码；发现问题指明模块。

## 12. providers：引擎适配与能力矩阵

### 12.1 适配器接口

每家一个适配器，实现：

```text
probe()            → 装没装、版本
capabilities()     → 见 12.2
login()            → 拉起该 CLI 自己的交互登录（PTY：内嵌终端或外部终端）；不做无头登录
auth_status()      → 已登录 / 未登录 / 失效
quota()            → 剩余 或 「未知」、重置时间、最近错误；没有可靠数字就写未知
build_args(role, module, fence, prompt_file) → 启动参数
run(args, cwd, stdin) → 归一化的事件流：init / text / tool / permission_request / permission_denied / api_error(分类) / result(含 session_id, 报告)
resume_args(session_id) → 恢复参数
```

登录注意（已确认）：Claude Code 的 `/login` 这类只在终端界面运行的内置命令在 `-p` 模式不可用，所以 `login()` 必须走 PTY，providers 不能只按 stdin/stdout 管道设计。

### 12.2 能力矩阵

角色对能力的最低要求：

| 能力 | 厂长 | 开发 | 审查 | 整合 |
|---|---|---|---|---|
| 无头非交互运行 | 需（或长驻无头） | 需 | 需 | 需 |
| 按 session_id 恢复 | 需 | 需 | 宜 | 宜 |
| 结构化输出 | 宜 | 需 | 需 | 需 |
| 路径级权限 / 可写根 | 宜 | 需 | 宜（只读） | 宜 |
| MCP 客户端 | 需 | 否 | 否 | 否 |
| 能跑 shell / 测试 | 需 | 需 | 需 | 需 |
| 权限宿主（在线审批） | 否 | 宜 | 否 | 否 |

各家现状：

| 引擎 | 状态 | 备注 |
|---|---|---|
| Claude Code | 已确认满足全部 | `-p`、`--resume`、`--output-format json/stream-json`、`--json-schema`、`--allowedTools`、`--permission-mode`、`--permission-prompt-tool`、`--add-dir`、`--max-turns`、`--append-system-prompt-file`、`--mcp-config`。风险见 R2。 |
| Codex | 待探测 | 无头模式、resume、沙箱可写根、结构化输出、MCP 客户端，逐项确认后填表 |
| Grok | 待确认 | 是否有官方 agent CLI、能否无头与 resume。若只有对话模型，则不能当工人，只能等以后 |
| Antigravity / Gemini | 待确认 | Antigravity 据了解是 IDE 而非可编程 CLI；可驱动的可能是 Gemini CLI。先确认再决定接哪个 |
| DeepSeek（API） | 已有 | 走现有消耗插件；作为工人需自行实现 agent 循环，第一版不当工人，只在设置页占一行 |

roles 页对缺能力的引擎在对应角色下置灰，保存时校验，不等到派活失败。

## 13. roles 与设置页

**岗位表**：厂长 / 开发 / 审查 / 整合 → 引擎 + 模型 + 思考档 + 每工单上限（回合、墙钟）+ 会话过长阈值 + 审查打回上限 + 并发数。

- 改表只对下一单生效；进行中工单锁开工时的绑定。
- 某角色的引擎未登录或额度见底，保存时提示。
- 建议（不强制）：开发和审查不绑同一引擎 + 同一模型。

**员工登录**：五家各一行：登录按钮（拉起 PTY 登录）、登录态、剩余或「未知」、重置时间、最近错误。

额度见底时：该工人停（红），厂长通知用户，不自动偷换模型。

## 14. 界面

**中间：厂长对话。** 项目全周期沟通、设计、派活、验收、交付都在这里。厂长的结束语行可高亮。

**右侧：工人列表。** 单纵向列表，中间分割，上方正在运行，下方已完成。

一行显示颜色点、角色、模块名、reason 的一句短状态和用于验收的 session_id 短码。点开后显示 DSH 数据目录中的归一化流日志、收工报告、审查结论、围栏申请（可批准 / 拒绝 / 此类全自动）和出错原文；没有输入框。

| 颜色 | 含义 |
|---|---|
| 绿 | running |
| 黄 | paused，有申请或需要用户 / 厂长处理 |
| 红 | failed |
| 无色 | done（会话仍在，可被追加） |

**设置页**：岗位表 + 五家登录 / 额度。

**项目条（最小）**：当前仓库路径、测试是否在绿、是否有未提交改动、厂长状态（回合中 / 等待：…）。

## 17. 第一版验收

本机已装并登录 Claude、Codex、Grok（Antigravity / DeepSeek 能探测到的也列出）之后：

1. 设置里能拉起各家登录，能看到各自额度或「未知」及重置时间。
2. 能保存示例岗位：Claude 厂长，Grok 审查，Codex GPT-5.6 Terra max 开发，Codex GPT-5.6 Sol 整合；缺能力或未登录的组合保存时被提示。
3. 打开一个业务仓库，厂长完成依赖和脚手架后切出至少两个模块，每个模块目录内有 README 工单。
4. 两只开发会话分别出现在右侧上方，绿；完成后到下方，无色。
5. 对厂长说改某个已完成模块，该行回到上方，session_id 短码不变。
6. 审查打回后，仍是原开发会话修复，不经厂长。
7. 工人要新依赖时停成黄，厂长装完 append 后继续。
8. 写出围栏则黄，不在围栏内弹窗；右侧批准后继续。
9. 额度尽或断网，工人停，厂长说明原因并给出两个选项；用户选换工具后，新会话从 `docs/log` 恢复接着干。
10. 只有厂长经 `crew.commit` 提交；工人 running 时提交被拒；`docs/`、`tests/` 中记录和测试未被删。
11. 关掉 DSH 再打开，厂长会话续得上，右侧列表与 board 一致。
12. 厂长每回合末尾有 `等待：…` 行；进度事件不唤醒厂长。
